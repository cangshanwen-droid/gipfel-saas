## 一、系统是什么

**Gipfel 合同管理系统**是一套面向工程/区域管理场景的金融级管理平台，由两部分组成：

| 部分 | 形态 | 技术栈 | 作用 |
|------|------|--------|------|
| **云端 SaaS** | 双服务 + Nginx | FastAPI + SQLite (WAL) + JWT | 数据唯一事实源，多人多机共享 |
| **桌面端** | Windows 安装包 | Electron + React + TypeScript | 用户操作界面，固定连云端 |

**核心价值**：不同电脑、不同人、同时使用，数据全云端统一；主席/代表分级权限，合同、资金、股票数据强隔离。

## 二、部署架构（云端 106.54.26.86）

```
用户桌面端 (Electron)
    │  HTTPS (443, 自签名证书)
    ▼
Nginx (80 → 301 → 443)
    ├── /api/*      → gipfel-api  :8000   （合同/资金/用户/公告/审计）
    └── /stock/*    → stock-api   :8001   （股票行情/交易/公司账户）
```

- **服务器**：腾讯云 Lighthouse 2核2GB（Ubuntu 20.04，实例 `lhins-o4kvhcw6`，**2026-09-10 到期待续费**）
- **数据库**：SQLite，**WAL 模式 + busy_timeout 5000ms**（多用户并发写安全）
- **安全**：ufw 仅开放 80/443/22；JWT 鉴权；管理端 X-Admin-Key 双因子
- **服务**：systemd 守护，gzip 压缩，单 worker uvicorn（并发安全）

## 三、已完成功能清单

### 3.1 合同管理
- 合同创建/编辑/审批/删除，类型化字段（销售/采购含税率）
- 合同编号自动生成（`CT-2026-0001`，并发冲突随机后缀重试）
- 明细自动计算：`tax_amount`、`total`（税率正确口径）
- 乐观锁（并发编辑 409 冲突提示）
- 审批流：审批通过后自动入账区域资金
- 合同入账 = 数据库原子 UPDATE（资金不丢失）

### 3.2 资金账户（区域级）
- 每区域独立资金账户（初始 10 万）
- 收支流水 + 幂等（**DB 级唯一索引**，5 并发同 key 只扣一次）
- 资金桥（stock-api ↔ gipfel-api 跨库转账）：幂等 key + 补偿 + X-Internal-Key

### 3.3 股票交易（公司级账户）
- 每**公司**独立股票资金账户（初始 10 万），与区域基建完全分开
- 主席（admin/operator）可买卖本公司股票；代表（rep）只读
- 买卖扣款 = 原子 UPDATE（实测 100000→99500 精确）
- 注入防护：POST /fund-accounts 仅主席可调 + 忽略 initial_balance 参数

### 3.4 公司管理
- 公司 ↔ 组织 1:1 关联（org_id 写回，数据隔离的基石）
- **用户多公司绑定**（v1.3.0 新增）：主席可管多家公司

### 3.5 公告管理
- 发布/删除/优先级（紧急/公告/通知）/按区域可见
- **发布者可修改**（默认当前登录人，可手填实际发布人）

### 3.6 用户与权限
- 三角色：**admin（管理端）/ operator（操作端=主席）/ rep（代表端）**
- 新建用户：角色选择 + 所属公司绑定
  - 代表端：单选公司（仅见本公司数据）
  - **操作端：多选公司（一人管多家，仅见绑定公司数据）**
- 密码规则：≥6 位且含字母+数字，bcrypt/PBKDF2 加密
- 用户管理（建/删/重置密码）、审计日志全记录

### 3.7 数据隔离（服务端强制）
| 角色 | 合同可见范围 | 股票操作 | 资金操作 |
|------|-------------|---------|---------|
| admin | 全部 | 全部公司可操作 | 全部 |
| operator（主席） | **仅绑定公司**（多家） | 仅绑定公司 | 仅绑定公司 |
| rep（代表） | 仅绑定公司（单家） | 只读行情 | 只读 |

- 隔离在**服务端**执行，忽略前端传入参数（防绕过）
- 跨公司详情访问 → 403

### 3.8 登录体系（多人多机）
- **账号统一云端**：管理员云端建号 → 任何电脑可用同一账号登录
- **兜底登录**：本地密码校验失败 → 云端验证 → 自动同步本地（新电脑首次登录自动建本地用户）
- 登录后存储本地凭据（safeStorage 加密）

### 3.9 系统监控
- 系统概览（活跃用户/资金/合同统计）
- 账户监控（管理端密钥访问，**缺失时自动创建默认密钥**）
- 审计日志（登录/操作全记录）

## 四、安全加固记录（重要！）

以下问题均在交付前审计发现并修复，**线上实测验证**：

| 级别 | 问题 | 修复 |
|------|------|------|
| **P0** | 资金桥越权：任意用户可传 username=admin 操作他人账户 | JWT 身份绑定（非 admin 只能操作自己；admin 可代操作） |
| **P0** | 资金桥幂等竞态：3 并发同 key 双扣款 | DB 级唯一索引（`uq_account_txn_idem_key`），5 并发实测只扣一次 |
| **H1** | 合同审批/创建无角色校验（rep 可建/审） | 限 admin/operator，rep 纵深防御 403 |
| **H2** | 合同数据无隔离（rep 可看全部） | 服务端强制 org 过滤 + 跨公司 403 |
| **H2** | 建公司 org_id 从未写回（公司与组织关联缺失） | `c.org_id = org.id` + 存量迁移补全 |
| **H1** | rep 可注入资金（POST /fund-accounts 无校验） | 仅主席可调 + 忽略 initial_balance + closed-db 修复 |
| **P1** | 管理端密钥缺失导致账户监控报错 | 自动创建默认密钥（多电脑开箱即用） |
| 中 | 合同隔离只匹配一家（text IN 绑定 bug） | 改 ORM 查询，实测两家全见 |

## 五、多用户并发能力（实测）

**5 用户并发实测**（2 operator + 3 rep，各绑独立公司）：

| 场景 | 结果 |
|------|------|
| 5 用户同时登录 | ✅ 5/5（约 290ms） |
| 5 用户同时查资金 | ✅ 各 10 万 |
| 2 主席并发买卖 + 3 rep 并发 | ✅ 主席 200 / rep 403 |
| 两家公司账户独立扣款 | ✅ 各扣 500 → 99500×2 |
| 2 主席并发建合同 | ✅ [200, 200]（SQLite 并发写安全） |
| 数据隔离 | ✅ rep 只见本公司，跨公司 403 |

**结论**：350 人规模日常并发完全够用。

## 七、使用细则速查

### 7.1 默认账号
- **admin / admin123**（云端 + 本地双库一致；首次登录建议改密）

### 7.2 典型操作流程
1. **管理员**：登录 → 公司管理建公司 → 用户管理建号（分配角色+公司）→ 公告发布
2. **主席（operator）**：登录 → 见自己管理的公司合同 → 股票买卖（本公司账户）→ 审批合同
3. **代表（rep）**：登录 → 见本公司合同（只读）→ 股票行情（只读）

### 7.3 绑定规则
- 建用户时：**操作端可多选多家公司**；代表端单选一家
- 用户绑定的公司 = 其可见/可操作范围（严格隔离）

### 7.4 管理端密钥
- 账户监控页需要管理端密钥：**自动创建**（无需手动配置）
- 也可手动：设置环境变量 `GIPFEL_ADMIN_KEY` 或 userData 下 `admin-key.txt`

### 7.5 密码规则
- ≥6 位，必须含字母和数字（前端+云端双重校验）
